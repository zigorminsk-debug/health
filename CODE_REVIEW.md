## A. Критические (падение / потеря данных пользователя)

### A1. Дубликаты `id` групп в `data.js` → TypeError и потеря введённых значений
`bud-zdorov/js/data.js:541` и `:815` — две группы с `id:"thyroid"`
(«Гормоны щитовидной железы» и «Щитовидная железа (полная панель)»);
аналогично `id:"vitamins"` встречается дважды (индексы 5 и 18).

Последствия (проверено прогоном в jsdom):

1. **Потеря введённых значений.** `app.js:539` (`gatherData`) сохраняет значения
   по ключу `group::test`. У дублей ключи совпадают (`thyroid::tsh`, `vitamins::vitd`
   и ещё 7), поэтому пустая строка из «расширенной панели» **перезатирает**
   введённое значение из первой панели. Проверено: ввёл ТТГ = 7.77 в первой
   группе → в сохранённой записи `thyroid::tsh = ""`.
2. **Падение `TypeError: Cannot read properties of undefined (reading 'type')`**
   в `evaluateRow` (`app.js:235`): для 13 показателей, которые есть **только** во
   второй группе (`atrtsh, tg, calcitonin, fol, homocys, k, na, cl, ca, cai, mg,
   phos, pth`), поиск `ANALYSIS_GROUPS.find(g=>g.id===gid)` возвращает первую
   группу, в которой такого теста нет → `t === undefined`.
   Места без защитной проверки `if (g&&t)`:
   - `app.js:259–265` — обработчик смены «Пол»: **падение при любом изменении пола**,
     цикл обрывается, статусы остальных строк не пересчитываются;
   - `app.js:620–624` — `loadSnapshot`: **падение при открытии сохранённой записи**,
     восстановление значений обрывается на первой «нерезолвленной» строке.
   (В `analyze()` проверка `if (g&&t)` есть — `app.js:441`, поэтому «Анализировать»
   не падает, но и не оценивает эти 13 показателей.)
3. Несовпадение референсов: у дублей `ft4` (9–22 против 10–23), `vitb12`,
   `zn`, `cu` диапазоны **разные**, а оценка всегда берётся из первой группы.

**Как чинить:** переименовать `id` вторых групп (например `thyroid_full`,
`vitamins_ext`) и добавить защитные `if (!t) return;` в `app.js:259–265` и
`app.js:620–624` (плюс в `evaluateRow` — ранний выход при `!t`). Старые
сохранённые ключи при этом продолжат читаться в первую панель, как и сейчас.

### A2. `clearBtn is not defined` после каждого распознавания OCR
`bud-zdorov/js/app.js:3501` — в блоке `finally` функции `runOCR`
(сигнатура на `:3346` — `(files, status, cancelBtn, preview)`) используется
`clearBtn`, который объявлен в **другой** функции (`initOCRCard`, `:3143`).
Чтение необъявленной переменной → `ReferenceError` из `finally`, который
перехватывается вызывающим `catch` (`:3172`). Итог для пользователя: после
**любого** (даже успешного) OCR вместо «✅ Готово…» выводится
«❌ Ошибка: clearBtn is not defined», а кнопка «🗑 Очистить сканы» не возвращается.
**Как чинить:** передать `clearBtn` параметром в `runOCR` или убрать строку 3501
(видимость кнопки уже восстанавливается в `:3165` при старте).

### A3. Неактуальная версия приложения в коде → вечный баннер «доступно обновление»
`bud-zdorov/js/app.js:5228` — `CURRENT_VERSION = '1.8.46'`, тогда как реально
1.8.48 (`index.html:274`, `build-apk.sh:47` `versionName`, `sw.js:1`,
`versionCode=66`). Проверка обновлений (`:5270`) сравнивает `latest` с 1.8.46 →
пользователям на 1.8.48 будет показываться «Доступна новая версия 1.8.48».

### A4. Android: объявлено разрешение CAMERA, но runtime-запроса нет
`apk-build/AndroidManifest.xml:13` (и `build-apk.sh:55`) объявляет
`android.permission.CAMERA`, однако в `MainActivity.java` нет ни
`requestPermissions`, ни `checkSelfPermission`. На Android 6+ запуск
`MediaStore.ACTION_IMAGE_CAPTURE` при объявленном, но не выданном CAMERA
бросает `SecurityException`:
- `MainActivity.startCamera()` ловит только `ActivityNotFoundException` →
  **краш приложения** по нажатию «📸 Сфотографировать/Снять на камеру»
  (мост `AndroidBridge.takePhoto`);
- в `onShowFileChooser` исключение глотает `catch(Throwable)` → выбор файла
  молча «ничего не делает».
**Как чинить:** убрать `uses-permission CAMERA` из манифеста (съёмка идёт через
системный интент, своё разрешение не нужно) либо запрашивать разрешение до
интента; и ловить `Throwable` в `startCamera()`.

### A5. Все внешние ссылки открываются внутри WebView
`MainActivity.java` — `shouldOverrideUrlLoading(WebView, WebResourceRequest)`
делает `v.loadUrl(...)` для **любого** URL и возвращает `true`. Поэтому
`tel:+375293371413` («О себе») даёт страницу ошибки внутри приложения,
а ссылка на APK (`https://csl.by/apps/budzdorov/BudZdorov.apk` из баннера
обновлений) уводит WebView с приложения. Нужен разбор схемы:
`file://` — грузить, `tel:`/`mailto:`/`http(s)://` — `Intent.ACTION_VIEW`
(или `AndroidBridge.openUrl`), остальное — reject.
Дополнительно: перегрузка с `WebResourceRequest` требует API 24, а `minSdk=21` —
на Android 5.x–6.x она вообще не вызывается (нужна и устаревшая
`shouldOverrideUrlLoading(WebView, String)`).

### A6. Обещание «данные переживут переустановку» не соответствует коду
`NativeStorage.java` хранит всё в `SharedPreferences`
(`/data/data/by.csl.budzdorov/...`), которые **удаляются при uninstall**.
При этом текст «О приложении» (`index.html`, блок «Обновления») и логика
подсказывают, что данные лежат в папке `BudZdorov` на внешней памяти и
переживут удаление старой версии; комментарий в `app.js:91–93` обещает
`/Android/data/by.csl.budzdorov/files/BudZdorov/`. Пользователь, последовавший
совету «удалите старую версию один раз», **потеряет весь журнал**.
**Как чинить:** либо реально писать в `getExternalFilesDir()` (файл/JSON),
либо исправить тексты и комментарий.

## F. Движок распознавания сканов анализов (аудит → v2, версия 1.8.50)

Жалоба: «очень плохо распознаётся, много ошибок». Проведён аудит OCR-конвейера
(`js/app.js`, ~660 строк) и сравнение с тем, как задачу решают специализированные
сервисы.

### F1. Как это делают специализированные сервисы (источники)

- **AWS Textract** возвращает не текст, а структуру: каждый элемент с bounding box
  и **confidence**; режимы FORMS (пары «ключ—значение») и TABLES (строки/колонки/
  ячейки). Документация прямо рекомендует использовать confidence для правил
  верификации: значения ниже порога отправлять на проверку человеку, а не подставлять
  молча. Таблицы распознаются лучше, когда ячейки визуально разделены и текст не повёрнут.
- **Azure Document Intelligence / Google Document AI**: готовые «табличные» модели
  со склейкой ячеек, типизированные блоки, дообучение на своих бланках; командам
  всё равно приходится писать постобработку для сборки полей из блоков.
- **Практики Tesseract (документация ImproveQuality + производственные руководства)**:
  ≥300 DPI, высота строчной буквы 20–30 px, бинаризация Otsu/адаптивная/Саувола для
  фото и неравномерной засветки (снижает CER на 30–50 %), PSM 6 для равномерного блока;
  **таблицы — известное слабое место Tesseract**, поэтому ячейки надо восстанавливать
  отдельно, по геометрии; слова с уверенностью <40 % помечать на ручную проверку,
  среднюю уверенность по странице логировать; словари `--user-words` с доменными
  терминами снижают подмены ~на 70 %; Tesseract.js «в лоб» даёт 85–90 % и для
  ответственного извлечения чисел требует препроцессинга и валидации.

Вывод: точность даёт не «лучший OCR», а связка **layout-анализ + confidence +
валидация доменными правилами + человек в контуре**.

### F2. Что было не так в v1 (причины ошибок)

1. **Layout не использовался.** Tesseract возвращает слова с координатами, но код
   брал только `data.text` и склеивал всё в строку. Колонки бланка перемешивались,
   имя показателя и его результат искались «в тексте рядом».
2. **Поиск числа в окне 120 символов** после имени: в строке
   `Лейкоциты 10^9/л 4,9 4,0-9,0` первым «подходящим» числом оказывалось `9`
   из размерности `10^9/л` или граница референса — классическая ошибка.
3. **Придумывание десятичной запятой.** `extractCandidates` для каждого целого
   генерировал варианты со сдвигом (489 → 4,89 и 48,9) со штрафом всего 0,5 балла,
   а «ожидаемые» границы были экстремально широкими (от `lo*0.3` до `hi*5`),
   поэтому неправдоподобное значение всё равно проходило.
4. **Уверенность OCR игнорировалась полностью** — ни порога, ни проверки человеком.
5. **Единицы измерения не учитывались** (г/дл против г/л, мг/дл против ммоль/л).
6. **КРИТИЧНО (найдено сквозным тестом):** значения записывались в поле строкой с
   запятой (`inp.value='4,9'`), а поля у нас `<input type="number" step="any">`.
   Такой тип принимает только точку — браузер отбрасывает строку, и поле остаётся
   пустым. То есть **все дробные результаты (4,9 / 0,45 / 9,5 / 2,1) не попадали в
   форму вообще**, даже когда OCR прочитал их верно. Это и давало ощущение
   «распознаётся очень плохо».
7. Препроцессинг — только ч/б + растяжка контраста (для фото с тенями мало);
   определение ориентации — 4 полных прохода OCR по изображению 1100 px (долго).

### F3. Что сделано (v2)

- **Новый файл `bud-zdorov/js/ocr-engine.js`** — чистый (без DOM) движок разбора:
  - `rowsFromWords` — строки таблицы кластеризацией слов по Y (порог 0,6 от медианной
    высоты слова); `cellsFromRow` — ячейки по X-зазорам (> max(2,2·ширины символа, 6 px));
  - `splitRowSegments` — бланки в две колонки (две логические строки на одной высоте);
  - `analyzeRow` — имя показателя = ведущие текстовые ячейки; значение = первая числовая
    ячейка, которая не является размерностью (`UNIT_CELL_RE`, шкала `10^9/л`) и не
    референсным диапазоном (`REF_RE`); склейка разорванной строки (имя на одной строке,
    число на следующей);
  - `matchAlias` — 73 словарные записи имён бланков (включая короткие аббревиатуры
    ПВ, ТТГ, CK, Fe, Ca, K, pH — только как отдельное «слово», чтобы `fe` не находилось
    внутри `ferritin`); выбор по наиболее длинному совпадению;
  - `UNIT_CONV` — пересчёт единиц (г/дл→г/л, мг/дл→ммоль/л для глюкозы/холестерина/
    ЛПНП/ЛПВП/ТГ, креатинин, мочевина, мочевая кислота, билирубин, кальций, железо);
  - `maybeShift` — сдвиг запятой **только** когда целое физически невозможно
    (> hi·4 или < lo·0.2) и результат попадает в lo·0.3…hi·3, с сохранением ведущих
    нулей («045» → 0,45, а не 4,5);
  - `parseNumTok` — починка типовых подмен OCR (O/o→0, l/I→1, B→8, З→3, S→5,
    разорванная запятая «9 , 5» → 9,5);
  - каждое значение несёт **confidence** (минимум по словам значения) и флаги
    `lowconf / range / shift / merged / unit:`;
  - `parseFromText` — строгий текстовый fallback, если координат нет.
- **`js/app.js`:**
  - `wordsFromTessData()` — собирает слова из `data.blocks→paragraphs→lines→words`
    (или `data.words`) с bbox и confidence;
  - `ocrAtAngle()` — единый конвейер для основного прохода и ручного поворота:
    препроцессинг `gray`, и **второй проход `otsu`** (бинаризация Отсу) только если
    первый неуверенный (средняя уверенность < 78 % или < 3 числовых слов); выбирается
    лучший проход по оценке `ocrPassScore` (уверенность слов + числовые слова + имена
    показателей);
  - `preprocessImageForOCR(source, mode)` — добавлен режим Otsu;
  - определение ориентации: образец уменьшен 1100 → 900 px (вдвое быстрее, точность
    та же — оцениваются только ключевые слова);
  - `fillAnalysesFromText()` переписан: теперь это тонкая обёртка над движком
    (геометрия → `parseFromWords`, иначе `parseFromText`); удалены мёртвые
    `aliases`, `pickTidAndVal`, `locateKey*`, `EXPECTED`, `extractCandidates`,
    `findNumberForTest`;
  - **`writeTestValue()` исправлен**: `type="number"` получает значение с точкой,
    списки (`<select>`) заполняются только при наличии подходящего варианта;
  - **панель проверки `#ocrReview`**: уверенные значения (≥60 %, в физиологических
    границах) вписываются сразу и получают кнопку «↩ отменить»; сомнительные
    (низкая уверенность / вне границ) НЕ вписываются и показываются с причиной и
    кнопками «Вписать» / «Пропустить» — правило «human in the loop» из Textract;
  - в отладочном блоке сырого текста теперь видны поворот, режим препроцессинга и
    средняя уверенность; итоговое сообщение сообщает число сомнительных значений.
